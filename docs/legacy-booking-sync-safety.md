# Safe legacy booking synchronisation

## Current admin control

The Django admin **Legacy synchronisation runs** page provides an audited control for the existing read-only matching-data import.

It can:

- run a source-count dry check;
- import only non-dormant locum Candidates and non-dormant clients with qualifying timesheet activity in the rolling previous 12 months, scoped to Doctors (`1`), Allied (`2`), Nursing (`3`), Assisted Care (`5`) and Radiology (`9`), together with the reference/rate/history data needed for that bounded projection;
- retain historical out-of-scope legacy Candidate, client and department rows inactive rather than deleting them;
- record the operator, timestamps, mode, status, source counts, imported counts, and safe failure message;
- prevent two reference-data syncs from running concurrently.

It cannot create, update, cancel, or delete a booking in legacy MySQL. Do not extend the current command with direct booking writes.

## Decision update — 17 August 2026

Outbound booking synchronisation remains **disabled**. The next integration step is a
read-only shadow import of legacy bookings plus item-level reconciliation; it is not a
direct-write extension of the current reference-data command.

Automatic outbound creation remains a no-go until all of the following are proven:

- immutable booking identity and explicit lifecycle/status semantics in the real legacy
  schema and VB.NET/ASMX paths;
- a unique legacy-side correlation UUID;
- one atomic legacy transaction that serializes Candidate scheduling and placement
  capacity, rechecks interval overlap and availability, and creates or rejects the
  booking;
- a PostgreSQL transactional outbox and database-backed worker with leases, stale-work
  recovery, idempotent retries, and read-back reconciliation;
- optimistic concurrency for updates/cancellations, item-level conflict quarantine,
  least-privilege write authority, and a tested canary/kill-switch runbook.

A query that locks only existing overlapping bookings does not serialize the zero-row
case. The approved legacy design therefore needs a stable Candidate scheduling mutex
row (or ordered Candidate-day reservation rows), as well as the relevant
vacancy/capacity lock, inside the same transaction as the booking insert.

The product priorities, staged implementation, go/no-go checklist, and required
concurrency tests are maintained in
[`booking-effectiveness-roadmap.md`](booking-effectiveness-roadmap.md).

## Required future authority model while both systems remain active

The following is required future behavior. It is not implemented by the current
admin control or management command. Until a controlled cutover, a future booking
integration must enforce these ownership rules:

1. A booking created in the old system must remain owned by the old system.
2. The future importer must identify that booking using its immutable legacy booking ID.
3. A future new-system booking must be new-system-owned and create an outbox event in the same PostgreSQL transaction.
4. A future integration worker must project that event to legacy MySQL once, read it back, and store the immutable legacy ID.
5. Neither system may overwrite a booking owned by the other system without an explicit conflict-resolution operation.
6. Cancellation must be an explicit state transition or tombstone, never inferred from a missing row.

## Required data contracts

Before enabling booking writes, identify the actual legacy booking/assignment tables and state transitions. Add or establish:

- `source_system`: legacy or new;
- immutable `source_booking_id`;
- immutable `correlation_id` generated by the new system;
- source `updated_at` or monotonically increasing version;
- last imported version/hash;
- explicit status mapping, including cancellation;
- one unique PostgreSQL mapping for each legacy booking ID;
- one unique legacy-side correlation ID for each new-system booking.

The safest option is a unique integration/correlation column or companion table in legacy MySQL. If legacy cannot enforce a unique correlation key, automatic outbound creation is not safe enough for production.

## Required future outbound protocol — not implemented

This outbound booking protocol is required future behavior. It is not implemented
by the current admin control or management command.

1. Inside one PostgreSQL transaction, validate and create the Booking and append an outbox event with a UUID correlation ID.
2. A durable queue worker claims pending events using row locks and `SKIP LOCKED`; the admin web request does not perform the legacy write.
3. Acquire a legacy-side serialization lock for the Candidate and time range, using a dedicated guard row or another proven transactional mechanism.
4. Re-read current legacy bookings for the Candidate and Shift/Facility while holding that lock.
5. Reject and quarantine the event if there is an overlapping Candidate booking, occupied Shift, changed legacy state, or ambiguous mapping.
6. Insert using the correlation ID. A retry first queries by correlation ID and treats an existing matching row as success.
7. Read the inserted row back and compare Candidate, Facility, role, start/end, and status.
8. Commit only after verification, then store the legacy ID and mark the outbox event delivered in PostgreSQL.
9. On timeout after an attempted legacy write, mark the outcome **unknown** and reconcile by correlation ID before retrying. Never blindly insert again.

## Required future inbound protocol — not implemented

This inbound booking protocol is required future behavior. It is not implemented
by the current admin control or management command.

1. Import incrementally using a reliable legacy version, updated timestamp plus stable tie-breaker, or append-only event source.
2. Upsert by immutable legacy booking ID, never by names.
3. Re-run all PostgreSQL mapping and overlap checks.
4. If a legacy booking conflicts with a new-system booking, preserve both source records and create a conflict requiring human resolution; do not use last-write-wins.
5. Advance the high-water mark only after all records in the page are durably imported or individually quarantined.

## Duplicate-booking barriers

All barriers are required; no single check is sufficient:

- unique correlation ID for retry idempotency;
- unique legacy-ID mapping in PostgreSQL;
- one confirmed Candidate per Shift/capacity rule;
- Candidate overlap validation in both systems;
- deterministic lock ordering around Candidate and Shift resources;
- compare-before-write against current legacy state;
- read-back verification;
- periodic reconciliation of Candidate, Facility, role, start/end, status, and source IDs;
- conflict quarantine with an operator-visible reason.

A derived fingerprint such as Candidate + Facility + role + start/end may help detect suspicious duplicates, but must not replace immutable source IDs because legitimate edits can change the fingerprint.

## Admin and operational controls for booking sync

Before exposing booking synchronization in Django admin:

- use a dedicated `run_booking_sync` permission;
- require a dry-run/reconciliation preview and explicit confirmation;
- enqueue a durable worker job rather than running in the HTTP request;
- permit only one booking-sync cycle at a time;
- log immutable per-record outcomes and counts;
- show conflicts and unknown outcomes separately from failures;
- support retry of failed events without replaying successful writes;
- alert when reconciliation counts or hashes differ;
- pilot with a small Facility set before broader rollout;
- keep an emergency switch that disables outbound writes while allowing inbound reconciliation.

## Cutover

Only after sustained clean reconciliation should ownership move from the old system to the new system. During cutover, stop old-system booking writes for the selected scope, complete a final inbound sync, reconcile, switch ownership, and then enable new-system outbound projection for that scope.
