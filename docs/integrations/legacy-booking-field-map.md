# Legacy booking projection field map

Status: **read-only discovery draft — outbound writes are not enabled**

This document defines the legacy shape that web-created bookings must reproduce. It maps the PostgreSQL domain to the existing MySQL vacancy header and item records; it does not copy the React/Django screen layout into MySQL.

## Verified legacy creation contract

The current desktop create flow inserts one `tbl_vacancies` header and one or more `tbl_vacancy_items` rows in a single MySQL transaction (`frm_vacancies_create.vb:30-88`, `Service.vb:4066-4084`). The vacancy number is generated by `LAST_INSERT_ID()` and is used by all child rows.

The production schema was inspected through the approved read-only account. No write was attempted.

The new exporter must preserve this pattern rather than deleting or overwriting the only history row.

## Rate compatibility

The item `rate` is the candidate **pay** rate, not the bill rate. The current Django `Shift` has both `pay_rate` and `bill_rate`; only the pay snapshot maps to `tbl_vacancy_items.rate`. Billing remains available in PostgreSQL and in the legacy client-rate tables/timesheet process.

The old create form only auto-classifies weekday, Saturday and Sunday (`rate_type` 1/2/3), but the legacy database supports the full 13-band taxonomy. Export must use a centralized, signed-off resolver and store the resolved type/rates immutably before enqueueing an event.

## Required architecture

1. Save the PostgreSQL vacancy/shift/booking change and a versioned `LegacySyncEvent` in the **same PostgreSQL transaction**.
2. A separate worker claims outbox events with row locking; browser requests never write MySQL.
3. The worker converts the event into a versioned legacy header/item command using this field map.
4. A new least-privilege MySQL writer account performs parameterized writes or DBA-approved stored procedures. The existing read-only profile is never reused or upgraded.
5. Header and child rows are written in one MySQL transaction.
6. A durable idempotency key/source mapping prevents duplicate vacancies or items after retries and process crashes.
7. The worker reads every written row back and compares all mapped fields before marking the event successful.
8. Retryable failures use bounded backoff; mapping/data conflicts become visible dead-letter records.
9. Administration exposes sync state, mapped legacy IDs, last verification and permissioned retry/reconcile actions.
10. Rollout proceeds through shadow payloads, a disposable schema, production read-only reconciliation, then an allow-listed pilot client.

## Blocking gaps before a writer can be built

- Add or derive signed-off legacy values for primary contact, desk, assigned user, job type, work level and recipient.
- Add immutable `legacy_rate_type`, pay and bill snapshots to each exported shift.
- Decide `shift_group` semantics for one-position and multi-position shifts.
- Confirm every status/completion transition against timesheet, payroll, invoice and notification behavior.
- Decide whether web-created candidates without `legacy_mysql_id` are blocked, manually linked, or created through a separate approved candidate-sync workflow.
- Define an integration mapping/idempotency table approved by the DBA.
- Capture a synthetic or protected known-good old-system vacancy as a golden contract fixture and compare every header/item value and side effect.
- Provision a separate writer identity with only the required procedures/tables and an emergency-disable feature flag.

No outbound write should be enabled until every blocking field has a deterministic source and the golden-record contract passes.
